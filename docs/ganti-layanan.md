# Jika Saya Mengganti Layanan atau API

Gunakan panduan ini untuk menyiapkan perpindahan setelah layanan pertama tersedia. Kerjakan satu perpindahan dalam satu waktu di staging dengan data uji. Sebelum mengganti nilai, simpan commit/image yang berjalan, konfigurasi sebelumnya di pengelola secret, informasi DNS, dan backup yang sudah diuji. Siapkan jendela perpindahan serta siapa yang dapat menjalankan pemulihan.

## Peta konfigurasi dan kode

**Lokal** berarti `.env.local` di root. **Hosting** berarti environment pada dashboard Render atau file privat `.env.production`/override staging pada Compose. Nama variabel tercantum di [.env.example](../.env.example). URL publik, nama host dan port dapat dicatat untuk operasi. Perlakukan URI database, password, token, `BETTER_AUTH_SECRET` dan `GOOGLE_CLIENT_SECRET` sebagai rahasia server. Hostname privat dan identitas admin juga perlu akses terbatas. Jangan menyalin nilai ke `NEXT_PUBLIC_*`, bundle browser, Git, atau screenshot.

## Contoh mengganti database

1. Dari root Madevi-Site, pilih commit yang sedang dipakai, pasang klien PostgreSQL yang cocok, dan siapkan database kosong di provider baru. Siapkan metode TLS dan batas jaringan. Simpan URI lama dan baru secara privat. Gunakan contoh bentuk di [panduan PostgreSQL](siapkan-layanan.md#postgresql--wajib).
2. Pada staging, ambil salinan dan jalankan restore sesuai [prosedur backup](../ops/backup-restore.md#buat-dan-periksa-cadangan). Cocokkan hitungan data, media dan checksum. Restore ke database kosong dahulu. Untuk versi aplikasi yang lebih baru, jalankan `npm run db:migrate` pada database target setelah restore dan verifikasi kompatibilitas.
3. Ubah `DATABASE_URL` pada staging, restart, lalu cek `/api/health/ready`. Uji login, baca/terbit konten, avatar dan akses gambar laporan, notifikasi, serta pemulihan backup dari target.
4. Untuk pengalihan database berdata, jadwalkan jeda penulisan, ambil dump terakhir dan ulangi verifikasi sebelum menerima penulisan pada target. Bila gagal sebelum penulisan target, pulihkan URI lama. Setelah penulisan target, jangan menimpa data. Simpan kedua salinan dan rencanakan rekonsiliasi sebelum berpindah kembali.

## Contoh mengganti domain

1. Siapkan nama baru, catat record dan TTL lama. Tambahkan nama baru ke dashboard hosting atau Caddy, lalu arahkan DNS dan tunggu sertifikat valid. Gunakan origin baru seperti `https://staging-baru.example.invalid` sebagai contoh.
2. Jika Google aktif, daftarkan `https://staging-baru.example.invalid/api/auth/callback/google` di client staging. Biarkan konfigurasi lama tersedia selama transisi. Ganti `BETTER_AUTH_URL` pada hosting, restart, dan uji permintaan dari origin baru.
3. Coba login dan operasi akun, lihat tautan verifikasi/reset, dan uji callback provider. Situs menerima satu origin utama pada konfigurasi ini. Atur pengalihan dari domain lama setelah jalur baru lulus, dan siapkan kembali origin, DNS serta sertifikat lama jika perlu rollback.

## Contoh mengganti SMTP

1. Di dashboard email baru, verifikasi pengirim dan ambil host, port, access key dan secret untuk email transaksional. Pastikan hosting dapat menjangkau port. Siapkan dua alamat uji dan simpan kredensial lama sementara.
2. Isi empat variabel `SMTP_*` dan `MAIL_FROM` dengan set nilai baru. Gunakan env staging dan restart. [Contoh nilai dan sumber](siapkan-layanan.md#smtp-dan-pengirim--wajib-jika-membuka-pendaftaran-email)
3. Uji pengiriman verifikasi, perubahan email dan OTP reset. Periksa inbox dan status delivery. Jika ada timeout atau penolakan, periksa port, token, pengirim, TLS dan kuota. Pulihkan set lama dan restart bila tes gagal.

## Contoh mengganti kredensial OAuth

1. Dari dashboard Google, tambahkan client atau secret sesuai tujuan perubahan. Pastikan callback staging dan daftar penguji cocok dengan origin yang akan dipakai.
2. Simpan `GOOGLE_CLIENT_ID` dan `GOOGLE_CLIENT_SECRET` di env staging sebagai pasangan. Restart dan uji login dengan akun sintetis yang sebelumnya sudah dihubungkan. Periksa bahwa akun dan data terdahulu tetap terkait. Uji pula pembatalan persetujuan.
3. Bila perubahan berhasil, tindak lanjuti pencabutan kredensial lama sesuai prosedur pemilik. Bila gagal, kembalikan pasangan sah yang sebelumnya bekerja dan cek ulang callback. Perubahan penyedia identitas memerlukan rencana untuk akun yang sudah terhubung.

## API internal dan pihak ketiga

API menyediakan operasi dan format data yang dipakai program. Endpoint adalah alamat untuk satu operasi. API internal adalah route `/api/*` yang dibuat dan dioperasikan oleh Madevi. Browser memakai path relatif melalui [auth client](../src/lib/auth-client.ts) dan komponen, sehingga mengikuti origin situs. URL callback Google dan route auth tetap dilayani aplikasi, sedangkan verifikasi identitas bergantung pada Google melalui Better Auth. SMTP memakai Nodemailer dan protokol SMTP. Tidak ada klien payment, API katalog eksternal atau object storage yang dikonfigurasi saat ini. [Route API](../src/app/api), [dependensi](../package.json)

Untuk mengganti layanan Google atau beralih dari SMTP ke API HTTP, periksa metode autentikasi dan izin, SDK/adapter, format input dan respons, callback atau webhook bila dibutuhkan, batas waktu, retry dan pencegahan pengiriman ganda. Google memakai transport Better Auth. SMTP membatasi koneksi dan greeting masing-masing 5 detik serta idle 10 detik. Pool PostgreSQL sendiri membatasi koneksi hingga 5 detik dan query hingga 10 detik. Uji juga kegagalan layanan, respons setengah berhasil, dan penolakan akses. Jika kontrak berubah, perbarui kode server serta tes yang terpengaruh sebelum memindahkan data atau traffic. [Pool database](../src/lib/db.ts), [opsi autentikasi](../src/lib/auth-options.ts), [penanganan auth](../src/app/api/auth/%5B...all%5D/route.ts)
